# 3DH Key Schedule - RFC 9807 Implementation

## Overview

This document describes the Triple Diffie-Hellman (3DH) key schedule implementation compliant with RFC 9807 Section 6.2. The 3DH protocol establishes a shared session key between client and server through authenticated key exchange.

## RFC 9807 Compliance

### Version Constant

**Changed from**: `OPAQUEv1-`  
**Changed to**: `RFC9807`

The preamble now uses the official RFC designation as required by RFC 9807 Section 6.2.2.

## Preamble Construction

### RFC 9807 Section 6.2.2

The preamble is a transcript of the authentication exchange, constructed as follows:

```
Preamble(client_identity, ke1, server_identity, ke2):
  preamble = concat(
    "RFC9807",                              // Version constant
    I2OSP(len(context), 2), context,       // Context with length prefix
    I2OSP(len(client_identity), 2), client_identity,
    ke1,                                    // KE1 message serialized
    I2OSP(len(server_identity), 2), server_identity,
    ke2.credential_response,                // KE2 credential response
    ke2.auth_response.server_nonce,
    ke2.auth_response.server_keyshare
  )
```

### Component Breakdown

1. **Version**: `"RFC9807"` (7 bytes)
2. **Context Length**: 2-byte big-endian integer (I2OSP format)
3. **Context**: Optional application-specific context data
4. **Client Identity Length**: 2-byte big-endian integer
5. **Client Identity**: Client's identity (typically public key)
6. **KE1**: Serialized KE1 message containing:
   - credential_request.data
   - auth_init.client_nonce
   - auth_init.client_keyshare
7. **Server Identity Length**: 2-byte big-endian integer
8. **Server Identity**: Server's identity (typically public key)
9. **Credential Response**: Serialized credential response containing:
   - data
   - masking_nonce
   - masked_response
10. **Server Nonce**: Server's random nonce
11. **Server Keyshare**: Server's ephemeral public key

## Triple-DH Computation

### RFC 9807 Section 6.2.1

The Triple-DH protocol computes three Diffie-Hellman shared secrets:

```
TripleDHIKM(sk1, pk1, sk2, pk2, sk3, pk3):
  dh1 = SerializePublicKey(sk1 * pk1)
  dh2 = SerializePublicKey(sk2 * pk2)
  dh3 = SerializePublicKey(sk3 * pk3)
  Output concat(dh1, dh2, dh3)
```

### Client-Side DH Pairs

1. **dh1**: client_ephemeral_secret × server_ephemeral_public
2. **dh2**: client_ephemeral_secret × server_static_public
3. **dh3**: client_static_secret × server_ephemeral_public

### Server-Side DH Pairs

1. **dh1**: server_ephemeral_secret × client_ephemeral_public
2. **dh2**: server_static_secret × client_ephemeral_public
3. **dh3**: server_ephemeral_secret × client_static_public

## Key Derivation

### RFC 9807 Section 6.2.3

The `DeriveKeys` function derives all authentication keys from the Triple-DH output:

```
DeriveKeys(ikm, preamble):
  prk = Extract("", ikm)
  handshake_secret = Derive-Secret(prk, "HandshakeSecret", Hash(preamble))
  session_key = Derive-Secret(prk, "SessionKey", Hash(preamble))
  Km2 = Derive-Secret(handshake_secret, "ServerMAC", "")
  Km3 = Derive-Secret(handshake_secret, "ClientMAC", "")
  Output (Km2, Km3, session_key)
```

### Key Derivation Steps

1. **Extract**: Use HKDF-Extract with empty salt to derive PRK from IKM
2. **Handshake Secret**: Derive from PRK using "HandshakeSecret" label and hashed preamble
3. **Session Key**: Derive from PRK using "SessionKey" label and hashed preamble
4. **Server MAC Key (Km2)**: Derive from handshake_secret using "ServerMAC" label
5. **Client MAC Key (Km3)**: Derive from handshake_secret using "ClientMAC" label

### Outputs

- **Km2**: MAC key for server authentication (length: Nh bytes)
- **Km3**: MAC key for client authentication (length: Nh bytes)
- **session_key**: Shared session key for application use (length: Nh bytes)

## Functional Design

### Currying

All major functions are curried to support partial application:

```typescript
// Curried signature
const deriveKeys: (config: Config) => 
  (ikm: Uint8Array) => 
  (preamble: Uint8Array) => 
  Promise<Either<Error, Keys>>

// Usage with partial application
const boundDeriveKeys = deriveKeys(config)
const result = await boundDeriveKeys(ikm)(preamble)
```

### Either Monad

All fallible operations return `Either<Error, T>`:

```typescript
const result = await deriveKeys(config)(ikm)(preamble)

if (result.isRight()) {
  const { Km2, Km3, session_key } = result.unsafeCoerce()
  // Use keys
} else {
  const error = result.extract()
  // Handle error
}
```

### Side Effects

Functions are marked with their side effects:

- `@pure`: No side effects (pure computation)
- `@sideEffect Logging`: Only logging side effects
- `@sideEffect Crypto RNG`: Uses cryptographic random number generator

Example:
```typescript
/**
 * Construct preamble (RFC 9807 Section 6.2.2)
 * @pure (pure computation, no I/O or side effects)
 */
export const constructPreamble = (...)
```

## Usage Example

### Complete Flow

```typescript
import { create3DHOps } from './3dh-functional.js'
import type { KE1, KE2 } from './authentication-functional.js'

// Create bound operations
const ops = create3DHOps(config)

// 1. Compute Triple-DH IKM
const ikmResult = await ops.computeTripleDHIKM(dh1, dh2, dh3)
if (ikmResult.isLeft()) {
  throw ikmResult.extract()
}
const ikm = ikmResult.unsafeCoerce()

// 2. Construct preamble
const preamble = ops.constructPreamble(
  context,
  client_identity,
  ke1,
  server_identity,
  ke2
)

// 3. Derive keys
const keysResult = await ops.deriveKeys(ikm, preamble)
if (keysResult.isLeft()) {
  throw keysResult.extract()
}
const { Km2, Km3, session_key } = keysResult.unsafeCoerce()

// 4. Use keys for authentication
// ...
```

## Security Considerations

### Version String

The use of `RFC9807` as the version string ensures:
- Protocol version binding in the transcript
- Protection against cross-protocol attacks
- Clear identification of RFC 9807 compliance

### Key Separation

The three derived keys serve distinct purposes:
- **Km2**: Authenticates server to client
- **Km3**: Authenticates client to server
- **session_key**: Application-level encryption

This separation prevents key reuse across different contexts.

### Preamble Binding

The preamble binds all message components together:
- Client and server identities
- Ephemeral key shares
- Nonces
- Credential exchange data

This prevents message substitution and replay attacks.
